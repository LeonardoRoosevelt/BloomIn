# Design Review — student-photo-records
測試狀態：`pnpm test` → Test Files 16 passed (16) / Tests 132 passed (132)；`ec_gate.py tdd student-photo-records` PASS（2026-09-29）

## Blocking

1. **觀察**：`exportPhotoBackup`（`src/store/photoBackup.ts`）先把所有照片的原圖＋縮圖讀成 `Uint8Array`，再用 `zipSync` 產生一整份 zip；匯入端 `unzipSync` 也是整份解開。記憶體峰值約為「全部照片總大小 × 2 以上」。以每張原圖 300–600KB 估算，500 張就是數百 MB，iOS Safari 分頁很可能在打包途中被系統終止，老師只會看到 App 閃退、備份沒有產生。
   **問題**：你預期一位學生、以及整間畫室，最終會累積多少張照片？若會到數百張以上，照片備份是否要改成「分學生匯出」或串流打包（fflate 的 `Zip`／`Unzip`），還是先在實機量測上限、並在畫面上告知「一次最多 N 張」？
   **為何問**：照片備份是這些紙本紀錄唯一的保全手段；一個在資料量變大後才會失效的備份，失效的時間點正好是資料最有價值的時候。

2. **觀察**：常駐的「該備份了」橫幅（`src/components/BackupBanner.tsx`）與 README 的「⚠️ 資料保存」段落都只提到 JSON 資料備份，完全沒有提到照片。照片備份時間存在 `kv.photoBackupAt`，只在設定頁顯示「上次照片備份」，沒有任何提醒。依 coverage.md 的決定，v1 不做照片備份提醒。
   **問題**：老師只看橫幅與 README 時，會不會以為「資料備份」已經包含照片？是否至少要讓橫幅或 README 說清楚照片需要另外備份，即使不做到期提醒？
   **為何問**：刪除主畫面圖示會連照片一起刪掉；若老師誤以為已備份，損失的是無法重拍的紙本原件翻拍。

## 架構層

1. **觀察**：這個功能順帶改寫了全 App 的存檔機制（`src/store/useStore.ts` 的 `flushPersist` 串行化、`persistError`、`superseded`；`src/store/db.ts` 的 `blocked`／`blocking` 處理；`App.tsx` 的三種全螢幕狀態），但這些決策只記錄在照片功能的 coverage.md 與 tdd-log 裡。
   **問題**：這些全域的存檔／升級規則，要不要另外寫成一份獨立的決策紀錄（或 README 的一節），讓下一個改動存檔流程的人找得到？還是你認為留在本功能的 spec 裡就夠了？
   **為何問**：下一次改 `DB_VERSION` 或存檔流程的人，不太可能去翻「照片紀錄本」的規格。

2. **觀察**：資料備份把「產生內容」與「送出」分開：`buildBackup()` 是純函式，由 `BackupPanel` 呼叫 `shareFile()` 並寫入備份時間。照片備份則把讀 DB、打包、`shareFile()`、寫入 `photoBackupAt` 全部放在 `exportPhotoBackup()` 一個 store 函式裡。
   **問題**：兩種備份要維持各自的形狀，還是讓照片備份也拆成「打包（可測）」與「送出＋記錄時間（畫面層）」？若 Blocking 1 決定改成分學生匯出或串流，哪一種形狀比較好延伸？
   **為何問**：同一個 App 裡兩種備份流程長得不一樣，下一個人要改其中一種時容易套錯另一種的假設。

3. **觀察**：`useStore.ts` 的持久化區塊現在同時處理 debounce、串行化（`inFlight`）、失敗重試（`pending ??= state`）、讓出連線（`onSuperseded`）與錯誤狀態，而這些模組層級變數與 zustand store 本身交錯在同一個檔案。
   **問題**：你是否希望把持久化抽成一個獨立模組（例如 `store/persist.ts`），讓 store 只負責領域操作？還是目前的集中寫法比較符合這個專案的規模？
   **為何問**：存檔是最容易出現資料遺失的地方，這輪驗證就找到兩次交錯與競態的 bug；職責集中在一處時，較容易整體審視。

4. **觀察**：還原 JSON 資料備份（`importState`）是完整覆蓋。如果備份裡沒有某位學生，這位學生的照片仍留在 `photos` store 裡，但 App 沒有任何畫面能看到或刪除它們。這些照片仍占用空間，也會被照片備份匯出。匯入照片備份時會回報「找不到學生」的張數，但本機既有的孤兒照片沒有入口。
   **問題**：孤兒照片要不要有一個看得到的地方（例如設定頁顯示「N 張照片不屬於任何學生」並可清除），還是維持隱形、等資料備份還原後自然出現？
   **為何問**：看不到的資料會悄悄占用 iOS 有限的配額，而配額滿了之後，新增照片與日常存檔都會失敗。

5. **觀察**：`src/screens/StudentPhotos.tsx` 有 510 行，包含主畫面、縮圖、檢視器、雙指縮放與 `useObjectUrl`。雙指縮放是自製的，也是最需要在 iPhone 實機調整的部分，目前沒有單元測試。
   **問題**：接下來在實機調整縮放手感時，是否要先把 Viewer／ZoomableImage 拆成獨立檔案？（這就是先前重構建議第 3 項。）
   **為何問**：實機調整通常要來回改好幾次，檔案越大，每次改動影響的範圍越難判斷。

## DBML 層

1. **觀察**：`photos` 一筆記錄同時存放 `blob`（原圖）與 `thumb`（縮圖）。`listPhotosByMonth` 用 `getAllFromIndex` 取出整筆，再在記憶體中丟掉 `blob`。Safari 讀出 IndexedDB 裡的 Blob 時是否會延遲載入內容，目前沒有實測。
   **問題**：要不要趁現在還沒有使用者資料，把原圖拆到另一個 store（例如 `photoBlobs`，key 同 `id`），讓列表只讀中繼資料加縮圖？還是先在實機量測一本 200 張的紀錄本開啟時的記憶體，再決定？
   **為何問**：現在拆只是改 v2 的 upgrade；等使用者累積照片之後再拆，就需要一次搬移全部 Blob 的 v3 migration，而且要在 iOS 的記憶體限制下完成。

2. **觀察**：`photos.student_id` 在 `docs/schema.dbml` 裡宣告了邏輯關聯，但刻意不強制參照完整性。`students` 只能封存、不能刪除，所以孤兒照片只會從「還原 JSON 資料備份」或「先匯入照片、後還原資料」產生。
   **問題**：「學生永遠不會被刪除」是否是長期不變的規則？如果將來加入刪除學生，照片應該一併刪除、保留，還是擋下刪除？
   **為何問**：這個規則決定了孤兒照片是「暫時狀態」還是「永久垃圾」，也決定了日後刪除學生時 schema 要不要補上連帶刪除的規則。

3. **觀察**：匯入時 `createdAt` 只檢查是不是字串，沒有檢查是否為 ISO 格式；但列表用 `localeCompare` 作為同日排序的次要鍵，前提是它是 ISO 字串。App 自己產生的值一定是 ISO。
   **問題**：`createdAt` 是否要比照 `recordDate`，在 schema 與匯入驗證中都要求 ISO 8601？還是只影響排序，可以接受？
   **為何問**：schema 的 note 寫「ISO」，但沒有任何地方強制。影響很小，只是同日照片的排序可能錯亂。

4. **觀察**：`kv.photoBackupAt` 存在 IndexedDB，不在 AppState 裡，所以不會跟著 JSON 資料備份搬到新裝置。在新裝置還原兩份備份後，設定頁會顯示「上次照片備份：從未備份」。
   **問題**：這個「換裝置後重新計時」的行為是你要的嗎？（可以解讀成「這台裝置還沒備份過」，其實也算合理。）
   **為何問**：決定 `photoBackupAt` 的語意是「這台裝置」還是「這份資料」，會影響日後若要做照片備份提醒時放在哪裡。

## 無疑慮
- 依賴方向：`domain/photoImage.ts` 不依賴瀏覽器，也不依賴 store；瀏覽器 codec 在 `lib/imageCodec.ts` 中實作並由畫面注入。`importPhotoBackup` 由呼叫端傳入學生 id，照片模組因此不依賴 zustand。
- 測試只透過 seam：repository 用 fake-indexeddb 跑真的 IndexedDB 行為；只在瀏覽器邊界（codec、`put` 空間不足、交易中止）做替身。多處核心邏輯都經 verifier 以突變確認測試有效。
- 錯誤跨 seam：`addPhotoFiles` 與 `importPhotoBackup` 用結果物件區分「無法讀取」「空間不足」「缺檔」「找不到學生」，只有意料之外的錯誤會拋出，畫面分別處理。
- 併發：`updatePhoto` 的讀與寫在同一個交易裡；主 state 存檔已串行化；新增照片的連點由 `saving` 旗標與停用按鈕擋住。
- 索引：唯一的查詢條件 `studentId` 已有索引；排序在單一學生範圍內的記憶體中進行，這個規模下不需要複合索引。
- 升級相容：`DB_VERSION` 1→2 只新增 store，不動 `kv`，依 `oldVersion` 增量處理，並有測試保證既有 state 保留。
- Nullability：所有欄位都是 not null，空白說明是空字串，與 `domain/types.ts` 的慣例一致。

## 使用者決定（2026-09-29）

| 項目 | 決定 | 理由 |
|---|---|---|
| Blocking 1 備份記憶體 | **改為每位學生分開匯出**：設定頁照片備份區列出有照片的學生（姓名、張數、上次備份時間、匯出），另有「未歸屬的照片 N 張」列（匯出／二次確認後清除，0 張時不顯示）；匯入維持單一按鈕、接受任一份 zip、只合併 | 限制單一 zip 的體積；iOS 每次分享都需要使用者點擊，無法一鍵連續匯出多份。單一學生照片極多時仍可能有記憶體上限，待實機量測 |
| Blocking 2 照片備份認知 | 備份提醒橫幅加上「照片需另外在設定頁逐位學生備份」；README「資料保存」段落補照片備份說明 | 避免老師誤以為資料備份已包含照片 |
| 架構 1 全域存檔規則文件 | 寫 `docs/decisions/0001-persistence-and-db-upgrades.md` | 下一個改 DB_VERSION 或存檔流程的人找得到 |
| 架構 2 備份函式形狀 | 照片備份改成「打包為純函式、送出與記錄時間在畫面層」，與資料備份一致 | 分學生匯出本來就要重寫這段，順帶對齊 |
| 架構 3 抽出持久化模組 | 暫不做 | 剛修完競態且有測試守護；純搬移無行為收益卻碰最危險的路徑。有 ADR 可找到規則，下次真的要改存檔流程時再拆 |
| 架構 4 孤兒照片 | 做最輕量的「未歸屬的照片」列（見 Blocking 1） | 分學生匯出後，孤兒照片若沒有入口就完全無法備份 |
| 架構 5 拆 StudentPhotos.tsx | 暫不做，實機調整縮放時再拆 | 屆時才知道縮放元件需要的介面 |
| DBML 1 原圖另存 | 原圖移到 `photoBlobs` store（key 同 `id`），`photos` 只留中繼資料＋縮圖；DB v2 尚未部署，直接修改 v2 upgrade，不另開 v3 | 現在拆不需要搬移任何使用者資料 |
| DBML 2 學生刪除規則 | 維持「學生只能封存」；在 schema.dbml 註明日後若加入刪除學生，必須先決定照片的處理方式 | 決定孤兒照片是暫時狀態 |
| DBML 3 createdAt 格式 | 匯入時要求 ISO 8601，否則整份拒絕 | 列表同日排序依賴 ISO 字串 |
| DBML 4 備份時間語意 | 以「這台裝置」為準；改為每位學生各自記錄（kv `photoBackupAt:<studentId>`，未歸屬照片另用一個 key） | 換裝置後重新計時是合理的 |
